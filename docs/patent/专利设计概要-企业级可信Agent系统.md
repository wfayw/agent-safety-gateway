# 智能体执行安全网关专利设计概要

版本日期：2026-04-27

## 1. 最终收敛结论

经过技术、产品、商业和专利审查角度的多轮评审，本项目不再定位为“企业智能体运行时治理系统”这种大而全的平台，而应收敛为一个更简单、更直接、更容易落地的方向：

**Agent Safety Gateway，即智能体执行安全网关。**

一句话定义：

**在智能体调用企业工具前，分析该操作会影响哪些资源、风险有多大，并决定是否放行、阻断、审批、沙箱执行或改写参数。**

项目主线只保留一个核心专利：

**一种智能体工具调用的预执行影响范围分析与风险控制方法。**

原先的“上下文最小化”和“断言级校验”仍然有价值，但不作为第一主线：

- 上下文最小化：作为输入侧安全能力或第二批窄案。
- 断言级校验：作为输出侧安全能力，暂缓，等有具体场景和数据后再申请。

这样做的原因很简单：

1. 企业真正愿意付费的是避免 Agent 误删库、误改配置、误触发发布、越权调用 API。
2. 该问题清楚、痛点真实、工程可实现。
3. 审查员也更容易理解其技术问题、技术手段和技术效果。
4. 方案不依赖大而空的“本体”“知识图谱”“运行时治理”等概念包装。

## 2. 不再主打的方向

以下方向不再作为核心专利主线：

- 通用 Agent 平台。
- 通用 RAG 平台。
- 通用 GraphRAG。
- 通用 LLM Wiki。
- 普通多智能体编排。
- 普通知识库问答。
- 普通长期记忆。
- 普通 guardrails。
- 普通字段脱敏。
- 普通 LLM 输出校验。

这些方向要么已经平台化，要么容易被认为是常规工程组合。它们可以作为系统组件使用，但不能作为技术护城河。

## 3. 核心专利题名

建议题名：

**一种智能体工具调用的预执行影响范围分析与风险控制方法**

备选题名：

**一种面向智能体工具调用的执行前风险识别与分级控制方法**

不建议题名：

- 一种基于资源影响图的智能体工具调用预执行风险控制方法。
- 一种基于业务本体约束的智能体运行时治理方法。
- 一种企业级可信智能体系统。

原因是“资源影响图”“本体约束”“运行时治理”容易显得概念化。真正要保护的是“工具调用执行前的影响范围分析和分级控制”。

## 4. 核心技术问题

现有智能体在调用企业工具时，通常只知道：

- 调用了哪个工具；
- 参数是什么；
- 用户是否有大致权限；
- 工具是否成功返回。

但系统往往不知道：

- 这个调用会影响哪些真实资源；
- 是读操作、写操作、删除操作还是触发操作；
- 是否影响生产环境；
- 是否影响核心业务表、核心配置或外部客户；
- 是否会级联触发下游系统；
- 是否可回滚；
- 是否应该人工确认。

这会导致：

- 删除生产数据；
- 修改关键配置；
- 触发错误发布；
- 调错外部 API；
- 发送错误通知；
- 越权操作业务流程；
- 事故发生后无法追溯为什么当时允许执行。

因此，本专利要解决的不是“让 Agent 更聪明”，而是：

**让 Agent 在动手前先经过一次可计算的影响范围分析和风险分级控制。**

## 5. 核心方案

### 5.1 基本流程

1. 获取智能体生成的工具调用请求。
2. 解析工具调用请求，得到动作元组。
3. 根据工具类型和参数识别直接影响资源。
4. 根据资源依赖关系扩展间接影响资源。
5. 计算风险要素。
6. 根据风险等级输出控制决策。
7. 记录决策链路和证据。

### 5.2 动作元组

工具调用请求被标准化为动作元组：

```text
Action {
  actor          发起者
  task_purpose   任务目的
  tool_type      工具类型
  operation      操作类型
  target         目标资源
  parameters     调用参数
  environment    执行环境
  timestamp      时间
}
```

示例：

```text
Action {
  actor = agent_01
  task_purpose = 清理测试数据
  tool_type = SQL
  operation = DELETE
  target = orders
  parameters = status='PENDING'
  environment = production
}
```

### 5.3 影响范围分析

系统根据动作元组识别影响资源。

直接影响包括：

- 数据库表；
- 数据字段；
- API 资源；
- 文件；
- 配置项；
- 代码仓库；
- CI/CD 流水线；
- 消息队列；
- 审批流程；
- 云资源；
- 外部系统。

间接影响包括：

- 下游服务；
- 定时任务；
- 对账任务；
- 通知对象；
- 报表系统；
- 审计系统；
- 客户侧状态；
- 生产环境状态。

### 5.4 风险要素

风险判断至少包括：

- 操作类型：读、写、删、发布、触发、通知。
- 执行环境：开发、测试、预发、生产。
- 资源级别：普通资源、敏感资源、核心资源。
- 影响范围：单条、多条、批量、不可估计。
- 权限匹配：用户权限、Agent 权限、任务目的权限。
- 可回滚性：可自动回滚、需人工回滚、不可回滚。
- 历史异常：该工具或类似参数是否曾导致失败。
- 审批要求：是否需要人工确认或双人审批。

### 5.5 控制决策

系统输出以下任一结果：

- 允许执行；
- 阻断执行；
- 请求人工确认；
- 沙箱执行；
- 参数改写；
- 降级为只读操作；
- 要求补充任务目的；
- 要求重新生成工具调用。

## 6. 为什么它不是普通本体或知识图谱

本体和知识图谱描述的是“企业中有什么”：

```text
订单表属于交易系统。
交易系统依赖支付系统。
订单表是核心表。
手机号是敏感字段。
```

本专利描述的是“这一次操作会造成什么影响”：

```text
Agent 要删除 orders 表中的数据。
目标环境是生产。
目标表是核心表。
删除操作不可自动回滚。
影响范围不可估计。
因此阻断执行或要求人工审批。
```

区别在于：

- 本体是静态概念模型；
- 知识图谱是事实关系；
- 本方案是一次具体工具调用的执行前影响分析。

本体或知识图谱可以作为输入，但不是核心创新。核心创新是：

**从一次具体工具调用的参数中解析出影响资源，并在执行前生成风险决策。**

## 7. 为什么它不是普通策略引擎

普通策略引擎通常判断：

```text
用户 A 是否有权限调用工具 B？
```

本方案判断：

```text
用户 A 让 Agent 调用工具 B，使用参数 C，在生产环境对资源 D 执行删除操作，会影响哪些上下游资源，是否可回滚，是否应该放行？
```

普通策略引擎偏静态规则，本方案偏动态参数分析和影响范围推演。

如果只做到下面这种程度，不值得申请专利：

```text
DELETE 操作一律拦截。
生产环境一律审批。
敏感表一律禁止。
```

真正值得保护的是：

```text
根据工具类型和参数解析目标资源；
根据依赖关系扩展影响范围；
根据环境、操作、资源级别、影响数量和可回滚性计算风险；
根据风险等级输出不同控制动作。
```

## 8. 工具类型示例

### 8.1 SQL 工具

输入：

```sql
DELETE FROM orders WHERE status = 'PENDING';
```

解析结果：

```text
operation = DELETE
target_table = orders
filter = status='PENDING'
environment = production
```

风险判断：

- `orders` 是核心表；
- 操作是删除；
- 环境是生产；
- 影响行数未知；
- 不可自动回滚。

决策：

```text
阻断执行；建议先执行 SELECT COUNT 估算影响范围；必要时转人工审批。
```

### 8.2 API 工具

输入：

```http
POST /api/v1/customer/credit-limit/update
```

风险判断：

- API 涉及客户授信额度；
- 影响客户账户状态；
- 需要审批记录；
- 不能由 Agent 自动执行。

决策：

```text
要求人工确认或审批流授权。
```

### 8.3 CI/CD 工具

输入：

```text
deploy service=payment env=production version=v2.4.1
```

风险判断：

- 目标服务为支付服务；
- 环境为生产；
- 版本未通过完整回归测试；
- 依赖订单服务和对账服务。

决策：

```text
阻断发布；要求测试通过并生成发布审批。
```

### 8.4 配置工具

输入：

```text
update config payment.timeout=30000
```

风险判断：

- 配置项影响支付链路；
- 可能影响请求超时和重试；
- 需要灰度环境验证。

决策：

```text
沙箱执行或灰度执行。
```

## 9. 通用性如何保证

本方案不是为软件研发流程定制，而是通过三层结构保证通用性。

### 9.1 通用动作模型

所有工具调用都归一化为：

```text
谁，在什么任务目的下，通过什么工具，对什么资源，执行什么操作，使用什么参数。
```

### 9.2 资源适配器

不同行业只需要提供资源适配器：

- SQL 适配器；
- API 适配器；
- 文件适配器；
- CI/CD 适配器；
- 工单适配器；
- 金融交易适配器；
- 制造设备适配器；
- 医疗系统适配器；
- 政务审批适配器。

适配器负责把具体工具参数映射为统一的资源、操作和环境。

### 9.3 影响规则和风险策略

不同行业的资源不同，但风险要素类似：

- 是否核心资源；
- 是否生产环境；
- 是否涉及敏感数据；
- 是否批量影响；
- 是否可回滚；
- 是否需要审批；
- 是否影响下游系统。

因此，通用的是方法，不是资源清单。

## 10. 其他两个方向的降级处理

### 10.1 上下文最小化

上下文最小化有价值，但不作为第一主案。

它的问题是容易被理解为：

- 字段脱敏；
- RBAC；
- ABAC；
- DLP；
- 数据最小化；
- 文档级权限控制。

只有一个点值得保留：

**敏感数据不进入模型上下文，而只进入受控工具，Agent 只看到工具返回的结论或摘要。**

示例：

```text
Agent 需要判断两笔交易是否属于同一客户。
系统不把身份证号给模型。
系统调用受控匹配工具在内部使用身份证号比对。
Agent 只收到：匹配结果 = 是，可信度 = 0.98。
```

该点可作为主案的从属权利要求，也可作为第二批窄案。

### 10.2 断言级校验

断言级校验理论上有价值，但暂缓。

原因：

- 工程复杂度高；
- 容易变成 RAG + 引用 + LLM judge；
- 先案和开源实现会越来越多；
- 没有具体场景时容易写虚。

如果后续要申请，必须绑定具体场景，例如：

- 发布说明校验；
- API 兼容性校验；
- 生产事故复盘校验；
- 财务指标报告校验；
- 风控结论校验。

不要泛泛申请“企业知识生成断言级校验”。

## 11. 推荐权利要求骨架

### 11.1 独立权利要求核心步骤

一种智能体工具调用的预执行影响范围分析与风险控制方法，包括：

1. 获取智能体生成的工具调用请求；
2. 解析所述工具调用请求，生成包含发起者、任务目的、工具类型、操作类型、目标资源、调用参数和执行环境的动作元组；
3. 根据所述工具类型和调用参数确定直接影响资源；
4. 根据预设资源依赖关系确定间接影响资源；
5. 基于操作类型、执行环境、资源级别、影响范围、权限匹配结果和可回滚性生成风险等级；
6. 根据所述风险等级输出执行控制决策；
7. 记录所述动作元组、影响资源、风险等级和执行控制决策。

### 11.2 从属权利要求方向

从属权利要求可覆盖：

- SQL 工具调用的影响行数估算和写操作拦截；
- API 工具调用的资源路径映射和审批要求判断；
- CI/CD 工具调用的发布环境、测试状态和服务依赖判断；
- 配置变更的服务影响范围和灰度执行判断；
- 消息发送或审批流触发的外部影响对象识别；
- 敏感数据仅进入受控工具而不进入模型上下文；
- 执行前决策链路的记录和回放；
- 参数改写，例如将删除操作改写为只读统计操作。

## 12. 审查可授权性判断

该方向具备申请价值，但不能保证授权。授权取决于最终权利要求、说明书公开充分程度、最接近现有技术和审查答复质量。

为了提高授权概率，撰写时应做到：

1. 不堆“大模型”“本体”“知识图谱”“治理”等概念。
2. 明确工具调用请求如何被解析。
3. 明确直接影响资源和间接影响资源如何识别。
4. 明确风险等级如何计算。
5. 明确不同风险等级对应的控制动作。
6. 给出多种工具类型实施例。
7. 给出可量化技术效果。

可量化指标包括：

- 高风险工具调用自动执行比例下降；
- 生产环境误操作率下降；
- 删除、发布、配置变更等高危操作拦截率提升；
- 人工审批触发准确率提升；
- 执行链路可回放率提升。

## 13. MVP 验证方案

MVP 不做完整平台，只验证“工具调用前影响分析”这一件事。

### 13.1 MVP 场景

研发 Agent 接收缺陷修复任务，并尝试调用以下工具：

- SQL 查询工具；
- Git 或代码仓库工具；
- CI/CD 工具；
- 日志查询工具；
- 配置管理工具。

### 13.2 必须展示

1. Agent 生成一条高风险 SQL，系统识别影响生产核心表并阻断。
2. Agent 尝试发布生产服务，系统识别测试未通过并阻断。
3. Agent 尝试修改关键配置，系统要求灰度或人工审批。
4. 系统记录每次决策依据。

### 13.3 90 天成功标准

1. 接入至少 3 类真实工具。
2. 支持至少 5 种操作类型：读、写、删、发布、配置变更。
3. 可以输出放行、阻断、审批、沙箱、参数改写 5 类决策。
4. 有一组模拟或真实测试数据证明误操作风险下降。
5. 至少获得 1 个企业试点意向。

如果 90 天内只能做出“知识库问答 + Agent 调工具”，项目应停止或重定位。

## 14. 如何避免像 AI 生成的空泛专利

不要试图“规避 AI 生成检测”。正确做法是：

**确保申请文件不是空泛文本，而是由真实技术方案、真实工程材料和真实发明贡献支撑。**

专利审查员关注的不是是否使用 AI 辅助写作，而是：

- 技术方案是否清楚；
- 是否充分公开；
- 是否具有新颖性和创造性；
- 权利要求是否得到说明书支持；
- 是否只是抽象算法、商业规则或概念包装。

正式申请前应准备：

1. 系统架构图；
2. 工具调用解析流程图；
3. 动作元组数据结构；
4. 影响资源识别规则；
5. 风险等级计算示例；
6. 多个真实输入输出样例；
7. MVP 原型或代码；
8. 测试记录和指标；
9. 研发会议纪要或技术取舍记录；
10. 发明人对核心技术方案的实质贡献说明。

AI 可以用于头脑风暴、检索和初稿整理，但最终方案必须由真实研发人员和专利代理师收敛、验证和撰写。

发明人必须是对技术方案作出实质贡献的自然人。

## 15. 最终项目边界

本项目最终边界为：

- 不做通用 Agent 平台；
- 不做通用知识库；
- 不做普通 RAG；
- 不做普通多智能体编排；
- 不做泛化的“AI 治理平台”；
- 专注 Agent 工具调用前的影响范围分析和风险控制。

最终判断：

**这个项目可以继续，但第一阶段只做一件事：Agent 动手前，先判断会不会出事。**

如果这件事做硬了，才有产品价值、专利价值和商业价值。否则，继续扩展上下文防火墙、断言校验、本体构建等方向，只会让项目重新变复杂、变虚、变难落地。
