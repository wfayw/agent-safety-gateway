# 基于禁止副作用义务证明状态机的智能体工具执行许可控制发明专利交底书草案

> 重要说明：本文件是技术交底书草案，不构成法律意见，也不能保证授权率。正式提交前应由专利代理师基于正式专利库检索结果重写权利要求。
> 本版基于 `docs/patent/检索报告-禁止副作用义务证明状态机.md` 重写。检索后判断：宽泛 agent guardrail、tool call approval、capability token、broker、audit、workload attestation、secret release、admission attestation、gatekeeper、denied capabilities、dry-run 和 sandbox 方向均已存在近似公开。因此本交底书继续收窄，主发明点不再是“执行器画像 attestation”本身，而是：面向智能体工具执行器的负能力探测、无副作用差异校验、漂移触发重探测和许可绑定。

## 一、建议申请名称

一种基于禁止副作用义务证明状态机的智能体工具执行许可控制方法、系统、电子设备及存储介质。

备选名称：

- 一种智能体工具执行器不可执行能力证明和调用许可绑定方法。
- 一种基于负能力证明的智能体高风险工具执行控制方法。
- 一种面向 SQL、CI/CD 和配置执行器的无副作用验证与许可绑定方法。

## 二、最新检索后的申请策略

### 2.1 不再作为主创新的方向

公开检索显示，下列方向不能作为主创新：

1. agent 工具调用前拦截、审批、阻断。
2. pre-execution firewall、policy validation、risk scanning。
3. capability token、execution token、invocation-bound token。
4. capability broker、gatekeeper、admission controller。
5. workload / TEE / MCP server attestation。
6. 签名画像、签名元数据、secret release。
7. 普通 dry-run、普通 sandbox、普通审计日志。
8. 软件测试中的 side-effect observation / result comparison。

这些方向可作为背景技术或实施环境，但不应作为独立权利要求的唯一核心。

### 2.2 本版核心发明点

本发明的核心不是把“负能力探测、副作用差异校验、漂移重探测、许可绑定”四个功能简单拼接，而是把 agent 工具执行前的安全条件建模为一个可证明、可失效、可消费的状态机：

> 先根据智能体工具调用的所需执行模式生成 `ForbiddenEffectObligation`，即本次执行必须禁止发生的危险能力和副作用集合；再由负能力探测和副作用差异校验分别生成覆盖这些义务的证据；证据被汇总为 `ExecutorSafetyEvidenceState`；凭据、网络、endpoint、runner 或 namespace 漂移会使该状态失效；只有所有禁止副作用义务均被有效证据覆盖时，状态机才允许转移到 `PermitBindable` 并签发绑定证据版本的调用许可。

核心链路为：

```text
ToolCall / RequiredExecutionMode
-> ForbiddenEffectObligation
-> EvidencePlan
-> NegativeProbeEvidence + SideEffectDeltaEvidence
-> EvidenceCoverageMap
-> ExecutorSafetyEvidenceState
-> DriftInvalidation / EvidenceRefresh
-> PermitBindableState
-> PermitBinding / PermitDeniedEvidence
```

### 2.3 为什么不是功能堆积

本发明的各步骤之间存在强制数据依赖：

1. `ForbiddenEffectObligation` 决定必须证明哪些危险能力不可发生，例如 write denied、DDL denied、production deploy denied、external webhook not triggered。
2. `NegativeProbePlan` 和 `SideEffectProbePlan` 都不是独立安全检查，而是由 `ForbiddenEffectObligation` 自动派生。
3. `DeniedCapabilityEvidence` 和 `SideEffectDeltaEvidence` 都必须回填到同一个 `EvidenceCoverageMap`，用于判断每个禁止副作用义务是否被覆盖。
4. `DriftTriggeredReprobe` 不是单独的漂移检测功能，而是把已覆盖义务的状态从 covered 改为 stale 或 invalidated。
5. `PermitBinding` 不是单独的 token 绑定功能，而是状态机从 `EvidenceComplete` 转移到 `PermitBindable` 的唯一出口。

因此，四类动作共同实现的是同一个技术约束：未被有效证据覆盖的禁止副作用，不得获得真实 executor 调用能力。

### 2.4 与上一版 ExecutorProfileAttestation 的区别

上一版重点是 `ExecutorProfileAttestation`，容易被 workload attestation、SPIFFE、Sigstore、Confidential Containers Trustee、gatekeeper attestation 等公开资料压缩。

本版进一步收窄：

- `attestation` 只是证据包装形式，不是主发明点。
- 主发明点是 `NegativeProbePlan`、`DeniedCapabilityEvidence`、`SideEffectDeltaEvidence` 和 `DriftTriggeredReprobe`。
- 重点不是“签名声明 executor 安全”，而是“通过探测证明 executor 不具备某些危险能力，并通过副作用差异证明 dry-run/sandbox 未产生真实副作用”。

## 三、技术领域

本发明涉及计算机系统安全、智能体工具调用控制、数据库操作安全、软件发布安全、配置管理安全、执行器能力验证、副作用检测和审计追踪技术领域，尤其涉及一种在大语言模型智能体、自动化 agent、开发工具 agent 或运维 agent 调用 SQL、CI/CD、配置中心、脚本或云资源执行器之前，对执行器危险能力进行主动负能力探测、对 dry-run/sandbox 进行副作用差异校验，并将校验证据绑定到调用许可的方法及系统。

## 四、背景技术

随着大语言模型智能体被接入研发、运维、数据分析和企业内部工具链，agent 可以调用数据库、命令行、CI/CD、配置中心、云资源 API 或 MCP 工具。此类调用具有真实副作用，例如删除生产数据、发布未通过测试的服务、修改关键配置、触发外部部署 webhook 或写入生产命名空间。

现有方案通常从调用者或执行入口控制风险，例如审批、guardrail、capability token、broker、sandbox、dry-run 或 attestation。此类方案存在一个共同缺口：它们通常假设某个执行器的能力标签可信，例如“readonly SQL executor”、“dry-run deploy executor”或“config sandbox executor”。然而，在真实企业环境中，执行器能力标签可能与实际能力不一致。

例如：

- readonly SQL executor 实际可执行 `INSERT`、`DELETE` 或 DDL。
- dry-run SQL executor 在事务回滚外触发了异步 trigger 或外部副作用。
- dry-run CI/CD executor 实际触发了 deploy endpoint、webhook 或 artifact promotion。
- config sandbox executor 实际可写 production namespace。
- 执行器曾经安全，但凭据、网络、镜像、runner 权限或 namespace 配置发生漂移。

因此，仅证明调用者被授权、执行环境可信或 broker 已校验，并不足以证明 executor 对本次 agent 调用是安全的。

## 五、现有技术不足

现有技术至少存在以下不足：

1. 只验证 executor 的正能力，例如可读、可执行 dry-run，缺少危险负能力证明。
2. 只检查配置标签，缺少对写入、删除、DDL、生产发布、生产配置写入等危险能力的主动拒绝探测。
3. dry-run 结果通常只是计划输出，缺少与受控执行后实际副作用的差异校验；虽然软件测试领域已有观察副作用并比较结果的公开，但其目的通常是生成测试或判断测试稳定性，而不是证明 agent 工具执行器未触发禁止副作用并绑定调用许可。
4. sandbox 常被视为静态命名空间或环境标签，缺少 namespace、凭据和网络边界的综合探测。
5. 执行器安全证据过期或漂移后，调用许可仍可能继续使用旧证据。
6. 审计记录通常只能证明策略允许或拒绝，不能证明 executor 当时不具备危险能力。
7. 不同执行器类型的负能力证据缺少统一结构，难以绑定到 agent 调用许可。

## 六、要解决的技术问题

本发明要解决的技术问题是：

1. 如何将所需执行模式转换为本次执行不得发生的禁止副作用义务集合。
2. 如何根据禁止副作用义务自动生成证据计划，而不是手工配置零散安全检查。
3. 如何用负能力探测证明 readonly executor 不具备写入、删除或 DDL 能力。
4. 如何用副作用差异校验证明 dry-run executor 未产生真实副作用。
5. 如何用证据覆盖图判断每个禁止副作用义务是否被有效证据覆盖。
6. 如何在凭据、endpoint、runner、network policy 或 namespace 漂移后使证据覆盖状态失效并触发重探测。
7. 如何在许可拒绝时证明系统因存在未覆盖义务而没有发放真实 executor 可调用能力。

## 七、技术方案概述

本发明提供一种基于禁止副作用义务证明状态机的智能体工具执行许可控制方法，包括：

1. 接收执行器注册信息和智能体工具调用对应的 `RequiredExecutionMode`。
2. 根据所述 `RequiredExecutionMode`、执行器类型、目标环境和资源范围生成 `ForbiddenEffectObligation`。
3. 根据 `ForbiddenEffectObligation` 生成 `EvidencePlan`。
4. 依据 `EvidencePlan` 执行负能力探测任务和副作用差异校验任务。
5. 根据探测和校验结果生成 `DeniedCapabilityEvidence` 与 `SideEffectDeltaEvidence`。
6. 将上述证据回填到 `EvidenceCoverageMap`，判断每个禁止副作用义务是否被覆盖。
7. 根据 `EvidenceCoverageMap` 生成 `ExecutorSafetyEvidenceState`。
8. 当漂移事件发生时，将相关证据状态转为 invalidated 或 stale，并触发证据刷新。
9. 仅当 `ExecutorSafetyEvidenceState=EvidenceComplete` 且未过期、未漂移时，生成绑定证据状态或证据版本的调用许可。
10. 当任一禁止副作用义务未被覆盖或证据状态失效时，拒绝生成调用许可并生成 `PermitDeniedEvidence`。

## 八、关键数据结构

### 8.1 ForbiddenEffectObligation

`ForbiddenEffectObligation` 是由所需执行模式生成的禁止副作用义务集合，至少包括：

```json
{
  "obligationId": "feo-20260501-001",
  "requestHash": "sha256:request...",
  "requiredExecutionMode": "readonly",
  "executorType": "sql",
  "resourceScope": ["orders"],
  "forbiddenCapabilities": ["write", "delete", "ddl"],
  "forbiddenEffects": ["row_mutation", "trigger_side_effect"],
  "requiredEvidenceTypes": [
    "write_denial",
    "delete_denial",
    "ddl_denial",
    "no_row_mutation",
    "no_trigger_side_effect"
  ]
}
```

### 8.2 EvidenceCoverageMap

`EvidenceCoverageMap` 用于表示每个禁止副作用义务是否被证据覆盖，至少包括：

```json
{
  "obligationId": "feo-20260501-001",
  "executorId": "sql-readonly-prod-001",
  "coverage": [
    {
      "requiredEvidenceType": "delete_denial",
      "covered": true,
      "evidenceHash": "sha256:denied..."
    },
    {
      "requiredEvidenceType": "no_trigger_side_effect",
      "covered": true,
      "evidenceHash": "sha256:delta..."
    }
  ],
  "allObligationsCovered": true
}
```

### 8.3 ExecutorSafetyEvidenceState

`ExecutorSafetyEvidenceState` 是状态机中的证据状态，至少包括：

```json
{
  "stateId": "eses-20260501-001",
  "executorId": "sql-readonly-prod-001",
  "obligationId": "feo-20260501-001",
  "state": "EvidenceComplete",
  "safetyEvidenceVersion": "sev-20260501-abc123",

  "validUntil": "2026-05-08T10:00:00Z",
  "invalidatedBy": null
}
```

许可签发只允许发生在 `state=EvidenceComplete` 且未过期、未漂移的情况下。若任一覆盖证据缺失、过期或被漂移事件失效，状态转为 `EvidenceIncomplete`、`EvidenceExpired` 或 `EvidenceInvalidated`。

## 九、核心流程

### 9.1 禁止副作用义务生成

系统接收 agent 工具调用对应的 `RequiredExecutionMode`，并基于工具类型、目标环境、资源范围和执行器类型生成 `ForbiddenEffectObligation`。

示例：

- SQL readonly 的禁止副作用义务包括 row mutation denied、delete denied、DDL denied、trigger side effect denied。
- CI/CD dry-run 的禁止副作用义务包括 production deploy denied、external webhook denied、artifact promotion denied。
- config sandbox 的禁止副作用义务包括 production namespace write denied、production credential use denied、production write endpoint access denied。

后续所有探测计划和许可条件均由该义务集合派生。

### 9.2 执行器注册和危险能力推导

系统接收执行器注册信息。注册信息只作为声明，不直接作为许可签发依据。系统根据 executorType、environment 和 claimedCapabilities 推导必须被拒绝的危险能力。

示例：

- SQL readonly：必须拒绝 write、delete、ddl。
- SQL dry-run：必须证明 no_real_mutation、no_trigger_side_effect。
- CI/CD dry-run：必须拒绝 production_deploy、external_webhook、artifact_promotion。
- config sandbox：必须拒绝 production_namespace_write、production_credential_use、production_write_endpoint_access。

### 9.3 证据计划生成

系统根据 `ForbiddenEffectObligation` 生成 `EvidencePlan`。该计划将每个禁止副作用义务映射到一种或多种证据生成方式：

1. 危险操作拒绝类义务映射为 `NegativeProbePlan`。
2. 无副作用类义务映射为 `SideEffectProbePlan`。
3. sandbox 边界类义务映射为 namespace、credential 和 network endpoint 探测。

### 9.4 负能力探测计划生成

系统生成 `NegativeProbePlan`。探测任务不是普通健康检查，而是针对危险能力的拒绝探测。

探测任务必须满足：

1. 针对具体危险能力。
2. 具有明确预期结果。
3. 在受控资源或探测资源上执行。
4. 可采集副作用快照。
5. 探测失败时 fail-closed。

### 9.5 负能力探测执行

系统执行探测任务并记录结果。如果任一危险操作未被拒绝，系统不生成对应 `DeniedCapabilityEvidence`。

例如 SQL readonly executor 如果成功执行 `DELETE` 探测，则系统认定 delete_denial 不成立，任何要求 readonly 且禁止 delete 的 agent 请求均不得绑定该 executor。

### 9.6 副作用差异校验

对于 dry-run 和 sandbox executor，系统执行如下步骤：

1. 采集受控资源执行前快照。
2. 生成预测副作用列表。
3. 执行 dry-run 或 sandbox 操作。
4. 采集执行后快照。
5. 计算预测副作用与实际副作用的差异。
6. 若出现 forbiddenEffectsObserved，则证据失败。

副作用差异校验用于证明 dry-run/sandbox 不是只输出计划，而是通过资源快照、日志、artifact registry、webhook log 或配置版本证明未触发禁止副作用。

### 9.7 证据覆盖图和安全证据状态生成

系统将 `DeniedCapabilityEvidence` 和 `SideEffectDeltaEvidence` 回填到 `EvidenceCoverageMap`。只有当每个 `requiredEvidenceType` 都被有效证据覆盖时，`ExecutorSafetyEvidenceState` 才可进入 `EvidenceComplete`。

若任一禁止副作用义务未被覆盖，状态为 `EvidenceIncomplete`，不得签发调用许可。

### 9.8 安全证据版本生成

系统将负能力证明和副作用差异证据汇总为 `ExecutorSafetyEvidenceVersion`。该版本绑定：

- deniedCapabilities。
- sideEffectGuarantees。
- evidenceHash。
- credentialFingerprint。
- networkPolicyFingerprint。
- namespaceFingerprint。
- validUntil。
- signature。

### 9.9 漂移触发重探测

系统监听凭据、endpoint、runner image、network policy、namespace、CI/CD runner 权限、配置中心 ACL 等变化。任一变化触发旧证据版本失效，并生成 `DriftTriggeredReprobe`。

在重探测完成前，相关 executor 不得用于签发新的调用许可。

### 9.10 与智能体工具调用许可绑定

agent 工具调用被归一化并生成 `RequiredExecutionMode` 后，系统将其与 `ExecutorSafetyEvidenceVersion` 匹配：

1. required allowed capability 必须在 verifiedAllowedCapabilities 中。
2. forbidden capability 必须在 deniedCapabilities 中。
3. required side effect guarantee 必须在 sideEffectGuarantees 中。
4. `EvidenceCoverageMap` 必须显示所有禁止副作用义务均已覆盖。
5. `ExecutorSafetyEvidenceState` 必须为 `EvidenceComplete`。
6. evidenceVersion 必须 active、未过期、未漂移。
7. evidenceHash 必须可回放验证。

全部满足时，系统签发绑定 `safetyEvidenceVersion` 的调用许可。否则拒绝签发并记录 `PermitDeniedEvidence`。

## 十、典型实施例

### 10.1 SQL readonly 负能力探测

系统对 readonly SQL executor 执行：

1. `SELECT 1`，预期成功。
2. `INSERT INTO __asg_probe_table`，预期权限拒绝。
3. `DELETE FROM __asg_probe_table`，预期权限拒绝。
4. `CREATE TABLE __asg_probe_ddl`，预期权限拒绝。
5. 探测前后 checksum 比较，预期无变化。

只有写入、删除和 DDL 均被拒绝，且资源快照无变化，才生成 `deniedCapabilities=["write","delete","ddl"]`。

若 agent 请求 `SELECT * FROM orders`，所需执行模式为 readonly，系统可匹配该证据版本。若 agent 请求 `DELETE FROM orders`，该 executor 的负能力证明不能用于执行真实写操作。

### 10.2 SQL dry-run 无副作用校验

系统对 SQL dry-run executor 执行：

1. 生成 explain plan。
2. 在受控事务或影子库执行候选 SQL。
3. 检查探测表 checksum、trigger log、异步任务队列和外部事件日志。
4. 计算 `effectDelta`。

若 `effectDelta=[]` 且 `forbiddenEffectsObserved=[]`，生成 `sideEffectGuarantees=["no_real_mutation","no_trigger_side_effect"]`。

### 10.3 CI/CD dry-run 不触发真实部署校验

系统对 CI/CD dry-run executor 执行：

1. 对测试服务生成部署计划。
2. 采集 deploy endpoint 调用日志。
3. 采集 webhook 日志。
4. 采集 artifact registry promotion 状态。
5. 比较执行前后快照。

若只生成部署计划，且没有 deploy endpoint、webhook、artifact promotion 记录，生成 dry-run 证据。

### 10.4 配置 sandbox 边界校验

系统对 config sandbox executor 执行：

1. 写入 sandbox namespace 探测 key，预期成功。
2. 写入 production namespace 探测 key，预期拒绝。
3. 使用同一凭据访问 production write endpoint，预期拒绝。
4. 检查网络策略是否阻止 production write endpoint。

只有 sandbox 写成功且 production 写、生产凭据、生产 endpoint 均被拒绝时，生成 sandbox 证据。

### 10.5 漂移后自动失效

某 readonly SQL executor 已生成安全证据版本。随后 Vault 凭据轮换，系统检测到 credentialFingerprint 变化，旧证据版本被标记为 invalidated。

在重新执行负能力探测前，该 executor 不得用于任何新的 agent 调用许可。若 agent 发起只读请求，系统返回 `permitIssued=false`，reason=`evidence_invalidated_by_drift`。

## 十一、技术效果

本发明至少具有以下技术效果：

1. 将执行器能力证明从“能做什么”扩展为“不能做什么”。
2. 防止 readonly executor 实际具备生产写、删除或 DDL 能力。
3. 防止 dry-run executor 在计划生成外产生真实副作用。
4. 防止 sandbox executor 越界写入生产 namespace 或调用生产写 endpoint。
5. 将负能力证据和副作用差异证据绑定到 agent 调用许可。
6. 在凭据、网络、runner 或 namespace 漂移后自动失效旧证据并 fail-closed。
7. 提供可审计证据，证明某次许可签发依赖的是具体安全证据版本。

## 十二、与现有技术的区别

### 12.1 与 agent guardrail / approval 的区别

现有方案关注工具调用是否应被批准。本发明关注候选 executor 是否经探测证明不具备危险能力，以及 dry-run/sandbox 是否经副作用差异证明未触发禁止副作用。

### 12.2 与 capability token / broker 的区别

现有 token 或 broker 关注调用者是否有权限调用工具。本发明关注 permit 签发前是否存在与执行器绑定的负能力证据和副作用差异证据。

### 12.3 与 workload attestation 的区别

现有 workload attestation 关注代码、环境、镜像或硬件状态是否可信。本发明关注执行器功能行为是否满足安全边界，尤其是危险能力是否被实际拒绝、dry-run/sandbox 是否无禁止副作用。

### 12.4 与普通 dry-run 的区别

普通 dry-run 输出将要做什么。本发明进一步采集执行前后快照和外部副作用日志，计算 `effectDelta`，并将差异证据绑定到许可。

### 12.5 与软件测试 side-effect observation 的区别

软件测试中的 side-effect observation 通常用于生成测试断言、比较重复执行结果或剔除非确定性字段。本发明的 `SideEffectDeltaEvidence` 用于判断 AI agent 可调用 executor 是否触发 forbidden effects，并将该判断绑定到 `RequiredExecutionMode` 和调用许可；证据缺失或漂移时返回 `permitIssued=false` 和 `executorInvoked=false`。

### 12.6 与普通健康检查的区别

普通健康检查证明 executor 可用。本发明的负能力探测证明 executor 对特定危险操作不可用。

## 十三、拟保护的权利要求草案

### 13.1 独立方法权利要求草案

一种基于禁止副作用义务证明状态机的智能体工具执行许可控制方法，其特征在于，包括：

1. 接收可由智能体调用的工具执行器的注册信息，所述注册信息包括执行器标识、执行器类型、执行端点引用、声明能力、目标环境和凭据类别；
2. 接收智能体工具调用对应的所需执行模式；
3. 根据所述所需执行模式、执行器类型、目标环境和资源范围生成禁止副作用义务集合，所述禁止副作用义务集合包括至少一个禁止危险能力或禁止副作用；
4. 根据所述禁止副作用义务集合生成证据计划，所述证据计划将不同禁止副作用义务分别映射为负能力探测任务或副作用差异校验任务；
5. 执行所述负能力探测任务，获得负能力探测结果，所述负能力探测结果包括探测操作、预期拒绝结果、实际结果、危险能力是否被观察到以及资源快照变化；
6. 根据所述负能力探测结果生成负能力证明，所述负能力证明包括已被拒绝的危险能力集合和证据摘要；
7. 执行所述副作用差异校验任务，采集受控执行前后的资源快照、外部事件日志或配置版本，并计算副作用差异证据；
8. 根据所述负能力证明和副作用差异证据生成证据覆盖图，所述证据覆盖图表示所述禁止副作用义务集合中的每个义务是否被有效证据覆盖；
9. 根据所述证据覆盖图生成执行器安全证据状态；
10. 当所述证据覆盖图显示所有禁止副作用义务均被覆盖，且所述执行器安全证据状态未过期、未漂移时，生成绑定所述执行器安全证据状态或版本的调用许可；
11. 当至少一个禁止副作用义务未被覆盖、证据过期或证据被漂移事件失效时，拒绝生成调用许可并生成许可拒绝证据；
12. 将所述禁止副作用义务集合、证据覆盖图、执行器安全证据状态、调用许可状态和执行器调用状态写入审计记录。

### 13.2 独立系统权利要求草案

一种基于禁止副作用义务证明状态机的智能体工具执行许可控制系统，包括：

- 执行器注册模块，用于接收执行器注册信息；
- 禁止副作用义务生成模块，用于根据所需执行模式生成禁止副作用义务集合；
- 证据计划生成模块，用于将禁止副作用义务映射为负能力探测任务或副作用差异校验任务；
- 负能力探测计划生成模块，用于生成负能力探测计划；
- 负能力探测执行模块，用于执行危险能力拒绝探测；
- 负能力证明模块，用于生成 `DeniedCapabilityEvidence`；
- 副作用差异校验模块，用于生成 `SideEffectDeltaEvidence`；
- 证据覆盖模块，用于生成 `EvidenceCoverageMap`；
- 安全证据状态模块，用于生成 `ExecutorSafetyEvidenceState`；
- 漂移检测模块，用于检测凭据、网络、endpoint、runner 或 namespace 漂移并触发重探测；
- 许可绑定模块，用于根据证据覆盖图和执行器安全证据状态生成或拒绝调用许可；
- 审计模块，用于记录证据版本、许可状态和执行器调用状态。

### 13.3 从属权利要求方向

1. 如权利要求一所述的方法，其中执行器类型包括 SQL、CI/CD、配置中心、脚本或云资源 API 执行器。
2. 如权利要求一所述的方法，其中 SQL readonly 负能力探测包括写入拒绝、删除拒绝和 DDL 拒绝探测。
3. 如权利要求一所述的方法，其中 dry-run 副作用差异证据包括执行前后资源 checksum、trigger log、异步任务队列或外部事件日志。
4. 如权利要求一所述的方法，其中 CI/CD dry-run 副作用差异证据包括 deploy endpoint 调用日志、webhook 日志和 artifact promotion 状态。
5. 如权利要求一所述的方法，其中 config sandbox 负能力探测包括 production namespace 写拒绝、production credential 使用拒绝和 production write endpoint 访问拒绝。
6. 如权利要求一所述的方法，其中漂移包括凭据指纹、网络策略指纹、runner 镜像、endpoint 或 namespace 配置变化。
7. 如权利要求一所述的方法，其中调用许可绑定 requestHash、executorId、safetyEvidenceVersion、deniedEvidenceHash、sideEffectEvidenceHash、ttl 和 nonce。
8. 如权利要求一所述的方法，其中许可拒绝证据包括 permitIssued=false、executorInvoked=false、缺失负能力证明和缺失副作用保证。
9. 如权利要求一所述的方法，其中所需执行模式由资源影响子图编译得到。
10. 如权利要求一所述的方法，其中真实执行器只能由 ExecutorBroker 在校验绑定安全证据版本的调用许可后调用。

## 十六、授权风险和应对

### 16.1 主要风险

本案仍存在以下风险：

1. dry-run、sandbox、权限测试、健康检查本身是常规技术。
2. workload attestation、admission control、gatekeeper 和 secret release 已有公开。
3. denied capabilities 在 Kubernetes / OPA / Gatekeeper 等领域已有类似术语。
4. 软件测试领域已有 side-effect observation 和重复执行比较结果的公开。
5. 如果权利要求只写负能力或副作用检查，可能被认为是常规安全测试。

### 16.2 应对策略

申请时应将创造性集中在以下连续组合：

```text
agent 可调用执行器
-> RequiredExecutionMode
-> ForbiddenEffectObligation
-> EvidencePlan
-> DeniedCapabilityEvidence + SideEffectDeltaEvidence
-> EvidenceCoverageMap
-> ExecutorSafetyEvidenceState
-> DriftInvalidation / EvidenceRefresh
-> PermitBindableState
-> PermitBinding / PermitDeniedEvidence
```

不要把重点写成：

- agent guardrail。
- capability token。
- broker。
- broad attestation。
- 普通 health check。
- 普通 dry-run。
- 普通 sandbox。

### 16.3 授权可能性判断

不能承诺具体授权率。基于当前公开资料检索和技术收窄程度，初步判断：

| 申请方式 | 风险判断 |
| --- | --- |
| 宽泛 Agent Safety Gateway | 授权稳定性低 |
| 宽泛 executor attestation / signed profile | 中低 |
| 本版禁止副作用义务证明状态机，但无工程 MVP | 中等偏低到中等 |
| 本版 + SQL/CI/CD/config 三类真实证据覆盖图 + 漂移失效 + permit 绑定 | 相对更稳，但仍受 dry-run、side-effect observation 和 admission 技术压缩 |

不建议对外宣称超过 80%。更稳妥的表达是：本轮公开资料检索未发现完整同构方案，但发现多个近似公开方向，申请必须收窄到“禁止副作用义务 -> 证据计划 -> 证据覆盖图 -> 漂移失效 -> 许可状态转移”的连续状态机。

## 十七、最终建议

本交底书建议作为下一轮优先专利申请草案使用。若预算只能申请一个专利，优先申请本案，而不是宽泛 Agent Safety Gateway 主案。

但不能将本案对外表述为“已确认没有近似公开方案”。准确表述应为：

> 公开资料检索未发现完整同构公开方案，但已发现 attestation、admission、secret release、gatekeeper、dry-run、sandbox、denied capabilities 和软件测试 side-effect observation 的近似公开；申请时应将权利要求收窄到禁止副作用义务、证据计划、证据覆盖图、漂移失效和许可状态转移的连续状态机。

最终建议的申请标题为：

> 一种基于禁止副作用义务证明状态机的智能体工具执行许可控制方法、系统、电子设备及存储介质。
