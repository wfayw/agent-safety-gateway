> 检索日期：2026-05-01

> 拟申请名称：基于同推理上下文锚点保留证明的智能体高风险工具调用许可控制方法、系统、电子设备及存储介质。
> 检索范围：Google Patents、arXiv / OpenReview、IETF Datatracker、行业技术文档、Agent 安全与治理公开资料。
> 结论边界：本报告不是专利代理机构出具的法律检索意见，不能证明全球范围内“绝对不存在近似公开”。严谨结论只能表述为“本轮公开资料和专利入口检索未发现完整同构公开方案”。

## 1. 检索结论

不能确认“没有近似公开方案”。本轮正式化检索发现多个高相关近似公开方向：

1. context window / prompt assembly / context engineering。
2. agent provenance / context provenance / execution evidence。
3. policy compiler / temporal constraint / reference monitor。
4. contextual authorization mesh / tool-call sidecar。
5. MCP tool call approval / audit / identity credential。
6. verifiable execution record / signed receipt / tamper-evident evidence。

但本轮未发现完整同构公开以下连续组合：

```text
High-risk ToolCallCandidate
-> action-specific RequiredContextObligation
-> PromptAssemblyManifest of the same inference that produced the tool call
-> per-anchor ContextRetentionEvidence
-> ContextSufficiencyState
-> reground / reapproval / deny / downgrade transition
-> PermitDecision bound to context-retention evidence
-> ContextAdequacyEvidence proving model-visible decision context
```

因此，本方向仍有申请价值，但不能按“没有近似公开方案”对外表述。更准确的申请定位是：

> 不是发明上下文工程、provenance、工具授权或执行证据，而是将“生成该高风险工具调用的同一次模型推理是否实际保留了动作必要上下文”转化为许可前状态机。

## 4. 逐项对比

### 4.1 与 dynamic context window management 的区别

WO2025221751A1 已公开：

- 根据 token budget 动态装配 prompt。
- recent messages 原文保留，older content 摘要保留。
- function call / tool response 进入上下文后重新计算 token budget。

本案不能主张“动态装配 prompt”或“选择原文/摘要上下文”。本案应限定为：

- `RequiredContextObligation` 来自待执行高风险工具调用，而不是通用会话质量。
- `PromptAssemblyManifest` 是证明对象，而不是优化目标。
- `ContextRetentionEvidence` 决定是否签发工具执行许可，而不是决定下一次 prompt 质量。

### 4.2 与 PCAS 的区别

PCAS 已公开：

- 以 dependency graph 表达 tool calls、tool results、messages 的因果关系。
- 用 Datalog 派生策略判断。
- reference monitor 在执行前阻断违规动作。
- authorization depends on causal context。

这是本案最高风险近似公开之一。本案必须区分为：

- PCAS 重点是对 agentic system state dependency graph 做策略判定。
- 本案重点是对生成具体 tool call 的同一次模型推理输入做上下文保留证明。
- PCAS 可判断“是否有某个审批节点因果先于动作”，本案判断“审批备注或约束是否在模型生成该 tool call 时以规定保留模式实际可见”。
- 本案的状态变量是 per-anchor `retentionMode`、freshness、conflict、taint 和 coverage，而不是通用 graph predicate。

### 4.3 与 Agent-C 的区别

Agent-C 已公开：

- 形式化时序约束。
- 对工具调用 trace、输入输出和 runtime state 做约束检查。
- 在模型生成阶段阻止不合规工具调用。

本案不能主张“工具调用前形式化约束”本身。本案应限定为：

- 约束对象不是任意 temporal property，而是动作相关上下文锚点的保留义务。
- 证明对象不是整个 trace 是否满足时序逻辑，而是产生该 tool call 的 `PromptAssemblyManifest` 是否覆盖 required anchors。
- 技术效果是防止上下文驱逐、摘要失真、过期和反证遗漏导致的错误执行。

### 4.4 与 CAAM 的区别

CAAM 已公开：

- 代理 sidecar 拦截 Thought -> Action 之间的 tool call。
- 使用 Inference Boundary hash、SCO metadata、contextual risk score 做实时验证。
- 建立 contextual session 并发放 JIT scoped token。

这是另一项高风险近似公开。本案必须避开“contextual authorization mesh / sidecar / scoped token”的泛化表述，限定为：

- 本案不主张 mesh、token 或环境 attestation。
- 本案主张具体的 `RequiredContextObligation -> PromptAssemblyManifest -> ContextRetentionEvidence -> ContextSufficiencyState`。
- `Inference Boundary hash` 只能证明边界或配置，不能证明“某个动作必要上下文锚点是否在本次推理输入中以规定模式保留”。

### 4.5 PCAS、CAAM、Agent-C 的集中对比

这三个公开是本案最需要重点规避的近似公开。它们分别卡住本案的三个方向：

| 公开方案 | 已公开的强点 | 会攻击本案的点 | 本案必须收窄的区别 |
| --- | --- | --- | --- |
| PCAS | dependency graph、tool calls、tool results、messages、cross-agent provenance、reference monitor pre-execution block | 审查员可能认为本案只是把因果上下文用于执行前授权 | 本案证明对象必须限定为“生成该 tool call 的同一次模型推理输入”，且证据必须是逐锚点保留状态，不是通用 dependency graph predicate |
| CAAM | sidecar tool-call interception、SCO、Inference Boundary hash、contextual risk score、JIT scoped token | 审查员可能认为本案只是 contextual authorization / sidecar gating | 本案不主张 mesh、SCO、JIT token、risk score；主张动作相关上下文锚点是否在 prompt 装配清单中以规定模式保留 |
| Agent-C | temporal / state-dependent constraints、runtime guarantee、SMT 检查、constrained generation 阻止不合规 tool call | 审查员可能认为本案只是工具调用前形式化约束 | 本案不主张任意 temporal constraint；只主张上下文锚点保留义务、保留模式、时效、冲突和污染状态驱动 permit |

更具体地说：

1. **PCAS 解决“是否满足策略依赖关系”**。它可以表达某个审批、工具结果或消息是否在因果图上影响某个动作。本案要解决的是“该审批备注、工具结果或消息是否在生成该 tool call 的模型输入中仍以规定保留模式实际可见”。二者都关注上下文，但证明对象不同。
2. **CAAM 解决“上下文感知授权边界”**。它强调 sidecar、SCO、Inference Boundary 和 JIT token。本案要避免这些词成为权利要求核心，转而锁定 `RequiredContextObligation` 和 `PromptAssemblyManifest` 的逐项匹配。
3. **Agent-C 解决“时序和状态约束不被违反”**。它的强点是 formal temporal property 和 constrained generation。本案应避免写“检测不合规工具调用”，而写“高风险工具调用所需上下文锚点未被保留时，许可状态不能转移”。

建议独立权利要求中加入以下限定，以避开这三项近似公开：

```text
所述 prompt 装配清单为生成所述高风险工具调用候选的同一次模型推理对应的装配清单；
所述上下文保留义务包括至少一个动作相关上下文锚点及其最低保留模式；
所述上下文保留证据按每个动作相关上下文锚点分别生成；
当任一必需上下文锚点处于 missing、stale、conflicting 或 tainted 状态时，拒绝签发许可或触发重新 grounding / 重新审批；
所述许可绑定所述上下文保留义务、prompt 装配清单和上下文保留证据的摘要。
```

### 4.6 与 provenance / execution evidence 的区别

PROV-AGENT、NexArt、Attested Intelligence、OATS、AgentHook 均已公开不同形式的：

- agent prompt / tool / decision provenance。
- inputs / outputs / context 的 tamper-evident record。
- signed receipt。
- PreToolUse / PreLLMCall / PostLLMCall 事件。
- policy gate 和审计链。

本案不能主张“记录上下文证据”或“签名审计”。本案应主张：

- 审计证据服务于许可前状态机。
- 证据不是笼统记录上下文，而是覆盖特定 `RequiredContextObligation` 的 per-anchor retention evidence。
- permit 被绑定到 evidence hash，证据不足则不允许签发。

### 4.7 与中国 MCP 审批专利的区别

CN120670429B 和 CN120687329B 已公开：

- MCP gateway。
- tool call request approval。
- identity credential。
- built context / request context。
- tool call audit。
- sandbox code interpreter。

本案不能主张“MCP 网关 + 审批 + 审计”。本案应限定为：

- 审批通过本身不足以执行。
- 必须进一步证明审批备注、用户限制、工具结果、策略和反证上下文在生成 tool call 的推理输入中仍被保留。
- 若上下文只剩泛化 `approved` 或未认证摘要，则状态转移到 `ReapprovalRequired` 或 `RegroundRequired`。

## 5. 是否发现完整同构公开

本轮未发现同时公开以下全部要素的方案：

1. 以高风险工具调用候选为触发点。
2. 根据动作影响类别生成动作相关 `RequiredContextObligation`。
3. 获取生成该工具调用候选的同一次推理的 `PromptAssemblyManifest`。
4. 对每个必需上下文锚点生成 `ContextRetentionEvidence`。
5. 将保留证据转化为 `ContextSufficiencyState`。
6. 根据状态触发 permit、reground、reapproval、downgrade 或 deny。
7. 将 permit 与上下文保留义务、prompt 装配清单和保留证据 hash 绑定。

但必须强调：虽然没有发现完整同构公开，近似公开已经足够多，不能对外写“确认没有近似公开方案”。

## 6. 申请价值判断

### 6.1 有价值的原因

该方向仍然有高商业价值：

1. 长任务 agent 必然遇到上下文压缩、驱逐、摘要失真和工具结果遗忘。
2. 企业高风险工具执行需要证明“模型决策时实际看到了什么”，而不是只证明“系统曾经收到过什么”。
3. human approval、tool authorization 和 audit trail 都不能单独证明审批约束或用户限制在后续模型推理中仍被保留。
4. 该方案可以覆盖编码 agent、CI/CD agent、数据库 agent、邮件 agent、财务 agent、客服 agent。
5. 可作为企业 agent 安全基础设施的执行许可层，具备产品化价值。

### 6.2 授权风险

授权风险为中高，不适合对外宣称 80% 以上。

| 版本 | 授权风险 |
| --- | --- |
| “管理 agent 上下文，避免忘记信息” | 极高 |
| “记录上下文 provenance 并审计” | 高 |
| “上下文充分性分数决定工具执行” | 中高 |
| “上下文保留义务 + 同推理 prompt 装配清单 + per-anchor 保留证据 + 状态机许可” | 中等到中高 |
| 上述方案 + 真实 MVP + 证据样例 + 正式代理师检索 | 中等 |

## 7. 建议修改交底书和权利要求

### 7.1 必须加强的限定

权利要求应强调：

1. `PromptAssemblyManifest` 必须绑定到生成工具调用候选的同一次模型推理。
2. `RequiredContextObligation` 必须由待执行动作的影响类别生成。
3. `ContextRetentionEvidence` 必须逐个覆盖 required anchor，而不是整体 context score。
4. 证据状态必须驱动 permit 状态转移，而不是仅用于审计。
5. 对审批备注、用户最新限制、上游工具结果、反证信息至少给出实施例。

### 7.2 不建议主张的内容

不要主张：

1. 发明了 prompt assembly。
2. 发明了 context engineering。
3. 发明了 agent provenance。
4. 发明了 tool call approval。
5. 发明了 signed receipt。
6. 发明了 policy gate。
7. 发明了 context risk score。

### 7.3 建议改名

当前标题可保留，但建议进一步收窄：

> 基于同推理上下文锚点保留证明的智能体高风险工具调用许可控制方法。

这个标题比“上下文保留证明状态机”更强调区别点：

- 同一次推理。
- 上下文锚点。
- 保留证明。
- 许可控制。

## 8. 最终结论

不能确认“没有近似公开方案”。本轮检索已经发现高相关近似公开，尤其是 PCAS、Agent-C、CAAM、WO2025221751A1、CN120670429B、CN120687329B、NexArt 和 Attested Intelligence。

可以确认的是：

> 本轮公开资料和专利入口检索未发现完整同构公开“动作相关上下文保留义务 + 生成该工具调用的同一次模型推理 prompt 装配清单 + per-anchor 上下文保留证据 + 上下文充分性状态机 + 高风险工具许可签发/重新 grounding/重新审批/拒绝”的方案。

因此，本案仍是一个有商业价值、值得继续打磨的专利方向，但必须以窄权利要求、工程 MVP 和证据样例支撑，不能作为“宽泛 agent 上下文管理”或“宽泛工具授权”申请。
