## 二、发明名称

建议使用：

备选名称：

**一种面向智能体工具调用的执行前风险识别与分级控制方法**

不建议使用“大而泛”的名称，例如“企业级可信智能体系统”“基于知识图谱的智能体治理平台”。本案技术重点不是通用平台，而是智能体工具调用在真正执行前的影响范围分析和执行控制。

## 三、背景技术

大语言模型和智能体技术已能够根据自然语言任务自动调用外部工具，例如 SQL 工具、CI/CD 发布工具、配置中心工具、文件工具、API 工具和运维工具。与传统文本生成不同，智能体工具调用会对企业真实系统产生直接影响。

现有智能体工具调用控制通常采用以下方式：

1. 工具白名单或黑名单：限制智能体可调用哪些工具。
2. 用户权限校验：判断用户或智能体是否有权限调用某个工具。
3. 人工确认：在部分操作前弹出确认。
4. 执行后审计：工具执行后记录日志。
5. 提示词约束：要求智能体不要执行危险操作。

上述方式存在明显不足：

- 只判断“是否能调用工具”，没有判断“本次参数会影响什么资源”。
- 只关注直接工具名称，不能区分 `SELECT` 和生产环境 `DELETE` 的风险差异。
- 难以识别间接影响资源，例如删除订单表可能影响订单服务、对账任务和下游报表。
- 执行后审计不能阻止已经发生的误删、误发布或误改配置。
- 提示词约束不具备确定性，不能作为企业生产系统的执行安全边界。

因此，需要一种在智能体工具调用发送给目标工具之前，解析工具调用内容、识别影响范围、计算风险等级并控制是否执行的方法。

## 四、要解决的技术问题

本发明要解决的核心技术问题是：

**如何在智能体调用企业工具之前，根据本次工具调用的工具类型、操作参数、目标资源、执行环境和资源依赖关系，确定其直接及间接影响范围，并据此生成可执行的风险控制决策，防止高风险工具调用直接作用于真实系统。**

具体包括：

1. 如何将不同工具的调用请求标准化为可计算的动作元组。
2. 如何根据工具类型和参数识别直接受影响资源。
3. 如何根据资源依赖关系识别间接受影响资源。
4. 如何结合操作类型、环境、资源级别、影响范围、测试状态和可回滚性生成风险等级。
5. 如何根据风险等级输出允许、阻断、沙箱、审批或参数改写决策。
6. 如何让该决策真正影响 executor 是否被调用，而不是仅输出提示信息。
7. 如何记录完整审计链路，便于后续回放和取证。

## 五、技术方案概述

本发明提供一种智能体工具调用的预执行影响范围分析与风险控制方法，包括：

1. 在目标工具 executor 被实际调用前，拦截并获取智能体生成的工具调用请求。
2. 将工具调用请求解析为动作元组，动作元组至少包括发起者、任务目的、工具类型、操作类型、目标资源、调用参数和执行环境。
3. 根据工具类型和调用参数识别直接影响资源。
4. 根据资源依赖关系识别间接影响资源，并生成影响路径。
5. 根据操作类型、执行环境、资源级别、依赖影响范围、验证状态和可回滚性生成风险因子。
6. 根据风险因子计算风险等级。
7. 根据风险等级输出执行控制决策。
8. 通过工具执行守卫决定是否调用目标 executor。
9. 记录工具调用请求、动作元组、影响资源、风险因子、风险等级、执行决策和 executor 调用结果。

核心闭环为：

```text
Agent 任务
  -> ToolCallRequest
  -> ActionTuple
  -> 直接影响资源
  -> 间接影响资源
  -> 风险因子
  -> 风险等级
  -> 执行控制决策
  -> executor 是否调用
  -> 审计记录
```

### 保护点收敛说明：不是模块堆叠，而是执行前技术控制闭环

本案不宜将“Agent、资源目录、风险规则、审计、前端页面”等单独模块作为核心保护点。单独看，这些模块均可能被认为是常规工程组件，技术含量和创新性不足。

本案真正需要保护的是上述组件之间形成的**执行前技术控制闭环**，即：

1. 智能体生成的工具调用请求不是直接进入 executor，而是在 executor 前被拦截。
2. 拦截请求被解析为动作元组，使不同工具调用被统一成可计算的执行动作。
3. 动作元组中的工具类型、操作类型、目标资源、调用参数和执行环境用于识别直接影响资源。
4. 直接影响资源继续触发依赖遍历，得到间接影响资源和影响路径。
5. 直接影响资源、间接影响资源和动作元组共同生成风险因子。
6. 风险等级不是提示信息，而是生成可执行控制决策。
7. 执行控制决策输入工具执行守卫，由执行守卫决定 executor 是否被调用。
8. 审计记录保存的是“执行前为什么允许或阻断”的决策链路，而不是普通执行后日志。

因此，本案的独立权利要求应围绕以下组合关系组织：

```text
工具调用请求 -> 动作元组 -> 影响资源 -> 风险等级 -> 执行控制决策 -> executor 调用控制 -> 审计证据
```

如果权利要求只写“包括解析模块、资源模块、风险模块、审计模块”，容易被理解为业务系统拼装；如果写清楚上述输出输入关系和 executor 调用控制结果，则更容易体现技术手段、技术问题和技术效果。

### 不建议作为独立核心保护点的内容

以下内容可作为实施例或从属特征，不建议单独作为核心发明点：

- 单独的资源目录、资源影响图或知识图谱。
- 单独的风险评分规则表。
- 单独的审计日志。
- 单独的前端模拟器或看板。
- 单独的人工审批流程。
- 单独的字段脱敏或上下文过滤。

这些内容的价值在于支撑执行前控制闭环，而不是各自独立构成发明核心。

## 六、系统结构

一个实施例中，系统包括以下模块。需要注意，以下模块不是简单并列堆叠，而是按“前一模块输出作为后一模块输入”的方式构成执行前控制链路：

1. **工具调用请求接收模块**：接收智能体生成的工具调用请求。
2. **Agent Adapter 模块**：将真实或本地样例 Agent 输出转换为统一 `ToolCallRequest`。
3. **动作解析模块**：将 SQL、CI/CD、Config 等请求解析为 `ActionTuple`。
4. **直接影响资源识别模块**：将动作目标映射到资源目录中的资源记录。
5. **间接影响资源识别模块**：根据资源依赖关系遍历下游影响资源。
6. **风险因子生成模块**：生成操作、环境、资源级别、依赖范围、测试状态、可回滚性等风险因子。
7. **风险等级评分模块**：基于加权阈值和硬阻断规则生成 `low`、`medium`、`high` 或 `prohibited`。
8. **执行决策模块**：输出 `allow`、`block`、`require_approval`、`sandbox`、`rewrite` 或 `readonly`。
9. **工具执行守卫模块**：接收执行决策和原始工具调用请求，在目标 executor 前执行门控，根据决策决定是否调用 executor，并输出 executor 是否被调用的结果。
10. **参数改写模块**：对危险操作生成低风险替代请求，例如将 `DELETE` 改写为 `SELECT COUNT`。
11. **审计记录模块**：保存完整分析链路、执行控制结果和 executor 调用控制结果。
12. **审计回放前端模块**：展示场景模拟、风险决策和审计详情。

## 八、风险评分与决策规则

一个实施例中，风险评分模块采用确定性加权规则和硬阻断规则结合的方式。

### 1. 风险因子

- 操作类型：只读操作风险低；删除、发布、配置更新风险高。
- 执行环境：生产环境高于测试环境和开发环境。
- 资源级别：核心资源和敏感资源风险更高。
- 依赖影响：影响多个资源或存在下游服务时风险升高。
- 验证状态：CI/CD 场景中测试失败属于关键风险。
- 可回滚性：不可回滚或需人工回滚时风险升高。

### 2. 风险等级

风险等级包括：

- `low`：低风险。
- `medium`：中风险。
- `high`：高风险。
- `prohibited`：禁止风险。

### 3. 硬阻断规则示例

- 生产环境核心表 `DELETE`。
- 测试失败的生产发布。
- 不可回滚且影响核心资源的危险操作。

### 4. 决策映射

| 风险等级 | 控制决策 |
|---|---|
| low | allow 或 readonly |
| medium | sandbox 或 require_approval |
| high | require_approval 或 rewrite |
| prohibited | block |

## 九、实施例一：生产订单 SQL 删除阻断

### 1. Agent 任务

```text
请清理生产环境中状态为 PENDING 的订单，目标是释放订单队列积压。
```

### 2. 工具调用请求

```json
{
  "toolType": "sql",
  "environment": "production",
  "rawPayload": {
    "sql": "DELETE FROM orders WHERE status='PENDING'",
    "database": "orders-prod"
  }
}
```

### 3. 动作解析结果

```text
toolType = sql
operation = delete
target = orders
environment = production
```

### 4. 影响资源

- 直接影响资源：`orders` 生产订单表，核心级别 `critical`，敏感级别 `restricted`。
- 间接影响资源：`order-service`，依赖关系为 `reads_from`。

### 5. 风险因子

- 删除操作：`Destructive DELETE operation`。
- 生产环境：`production environment`。
- 核心资源：`critical resource: orders`。
- 多资源影响：`Multi-resource impact scope`。
- 手工回滚：`manual rollback capability`。

### 6. 执行决策

风险等级为 `prohibited`，执行决策为 `block`，且生成参数改写建议：

```sql
SELECT COUNT(*) FROM orders WHERE status='PENDING'
```

### 7. 技术效果

工具执行守卫在调用 SQL executor 之前阻断请求，executor 调用次数为 `0`，避免生产订单数据被直接删除。

## 十、实施例二：生产订单 SQL 只读查询放行

### 1. Agent 任务

```text

```

风险等级为 `low`，执行决策为 `allow` 或 `readonly`，SQL executor 被调用一次。

### 4. 技术效果

## 十二、实施例四：生产关键配置变更进入沙箱建议

### 1. Agent 任务

```text
请把 payment-service 的 payment.timeout 调整为 100ms，以减少用户等待。
```

### 2. 工具调用请求

```json
{
  "toolType": "config",
  "environment": "production",
  "rawPayload": {
    "service": "payment-service",
    "key": "payment.timeout",
    "value": "100ms",
    "previousValue": "2s",
    "namespace": "production"
  }
}
```

### 3. 风险判断

系统识别该请求为生产关键配置更新，直接影响 `payment.timeout` 配置项，间接影响 `payment-service` 和 `reconciliation`。

### 4. 执行决策

风险等级为 `medium`，决策为 `sandbox`，生成 staging/canary 改写建议，不直接调用生产配置 executor。

7. 能够通过参数改写建议将高风险操作转为低风险预估操作。

## 十五、建议权利要求保护点

建议权利要求以“执行前技术控制闭环”为核心，至少保护以下技术特征组合：

1. 在目标 executor 调用前拦截智能体工具调用请求。
2. 将工具调用请求解析为动作元组。
3. 基于动作元组中的工具类型、操作类型、目标资源、调用参数和执行环境识别直接影响资源。
4. 基于资源依赖关系由直接影响资源扩展得到间接影响资源和影响路径。
5. 基于动作元组、直接影响资源、间接影响资源和影响路径生成风险因子。
6. 基于风险因子生成风险等级。
7. 基于风险等级生成执行控制决策。
8. 将执行控制决策输入工具执行守卫，由工具执行守卫控制 executor 是否被调用。
9. 记录原始请求、动作元组、影响资源、风险因子、风险等级、执行控制决策和 executor 调用控制结果。
10. 将危险写操作改写为只读影响范围估算。
11. 对测试失败的生产发布设置硬阻断规则。
12. 对生产关键配置变更生成沙箱或灰度改写建议。

其中第 1 至第 9 项应作为独立权利要求主线；第 10 至第 12 项适合作为从属权利要求或实施例。

### 建议独立权利要求口径

建议独立权利要求不要写成“一个系统包括若干模块”，而应写成如下逻辑：

```text
在目标工具 executor 被调用前获取工具调用请求；
解析该请求得到动作元组；
基于动作元组确定直接影响资源；
基于资源依赖关系确定间接影响资源；
基于动作元组、直接影响资源和间接影响资源生成风险等级；
基于风险等级生成执行控制决策；
由执行控制决策控制 executor 是否被调用；
记录 executor 调用控制结果和风险决策链路。
```

这样的写法能突出组合后的功能相互作用和技术效果，降低被认定为普通业务系统组合的风险。
