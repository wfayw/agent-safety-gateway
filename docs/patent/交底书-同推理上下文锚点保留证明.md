# 基于同推理上下文锚点保留证明的智能体高风险工具调用许可控制发明专利交底书草案

> 重要说明：本文件是技术交底书草案，不构成法律意见，也不能保证授权。正式提交前应由专利代理师基于正式专利库检索结果重写权利要求。

## 一、拟申请名称

一种基于同推理上下文锚点保留证明的智能体高风险工具调用许可控制方法、系统、电子设备及存储介质。

备选名称：

1. 一种基于上下文保留证明状态机的智能体高风险工具调用许可控制方法。
2. 一种面向智能体工具调用的决策上下文充分性证明和许可控制方法。
3. 一种基于模型可见上下文证据的智能体高风险动作执行控制方法。
4. 一种将智能体高风险动作许可绑定至推理上下文保留状态的方法。

## 二、技术领域

本发明涉及人工智能智能体安全、工具调用控制、访问控制、上下文管理、审计取证和企业自动化执行安全领域，尤其涉及一种在智能体执行高风险工具调用之前，基于模型生成该工具调用时的上下文保留证明来决定是否签发执行许可的方法和系统。

## 二之一、正式检索补充结论

基于 `docs/patent/检索报告-同推理上下文锚点保留证明.md` 的正式化公开检索，本案不能对外表述为“确认没有近似公开方案”。已发现的高相关近似公开包括：

1. dynamic context window management，公开 prompt assembly、recent verbatim messages、older summaries、tool response 后重新计算 token budget。
2. PCAS / Policy Compiler for Secure Agentic Systems，公开 dependency graph、tool call、tool result、message provenance 和 reference monitor 执行前阻断。
3. Agent-C，公开对 LLM agent 的工具调用 trace、状态投影和时序约束检查。
4. CAAM / Contextual Agent Authorization Mesh，公开 sidecar 拦截 tool call、Inference Boundary hash、SCO metadata、Contextual Risk Score 和 JIT scoped token。
5. PROV-AGENT、OATS、NexArt、Attested Intelligence、AgentHook，公开 agent provenance、execution evidence、signed receipt、runtime hook event 等。
6. 中国 MCP 工具调用审批专利，公开 MCP gateway、tool call approval、identity credential、built context 和 full-link audit。

本轮检索未发现完整同构公开以下连续组合：

```text
High-risk ToolCallCandidate
-> action-specific RequiredContextObligation
-> PromptAssemblyManifest of the same inference that produced the tool call
-> per-anchor ContextRetentionEvidence
-> ContextSufficiencyState
-> reground / reapproval / deny / downgrade transition
-> PermitDecision bound to context-retention evidence
```

因此，本案仍有申请价值，但必须收窄为“同一次模型推理的上下文锚点保留证明驱动许可状态转移”，不能写成宽泛的上下文管理、provenance、tool approval 或 policy gate。

## 三、背景技术

企业级智能体可以在较长任务中调用数据库、代码仓库、CI/CD、邮件、CRM、工单、云资源、配置中心、支付和内部 API。现有安全方案通常在工具调用边界进行控制，例如：

1. 判断工具是否允许调用。
2. 判断参数是否命中危险模式。
3. 判断用户是否已经审批。
4. 判断凭证是否具备权限。
5. 判断操作是否符合策略规则。
6. 记录审计日志或执行轨迹。

上述方案解决的是“工具调用本身是否被允许”的问题，但没有充分解决另一个关键问题：

> 生成该工具调用的模型推理过程，是否实际具备作出该高风险决策所需的必要上下文。

智能体在长任务中经常发生上下文驱逐、摘要压缩、RAG 检索遗漏、memory 过期、多智能体任务转交、工具返回结果被摘要、审批备注被简化等情况。此时工具名和参数可能通过传统校验，但模型生成该参数时可能已经没有看到最新用户限制、审批约束、策略规则、上游工具结果、资源状态或反证信息。

例如：

1. 用户要求“不要发送给外部客户”，但该限制在上下文压缩后消失，智能体仍调用邮件发送工具。
2. 上游工具返回“订单已取消”，但当前推理只看到旧摘要，智能体仍调用退款或发货接口。
3. 人工审批只允许 dry-run，但后续上下文只保留“approved”，智能体执行真实部署。
4. 策略文件或配置状态已更新，但智能体仍依据旧上下文调用 CI/CD。
5. RAG 检索到反证文档，但摘要未保留反证字段，智能体调用写操作。
6. 上游 agent 转交任务时遗漏限制条件，下游 agent 产生高风险工具调用。

因此，仅记录“工具调用参数合法”或“用户点击同意”不足以证明该高风险操作是基于充分、最新、可信的上下文作出的。

## 四、现有技术缺陷

现有公开方向包括 context engineering、context window management、context provenance、tool authorization、human-in-the-loop approval、agent audit trail 和 policy compiler。这些方向分别存在如下缺陷：

1. context engineering 主要优化模型效果、token budget 和任务完成率，未将上下文保留状态作为高风险工具调用许可条件。
2. dynamic context window management 主要决定哪些消息、摘要或 memory 放入 prompt，未证明本次工具调用所需上下文是否被保留。
3. context provenance 和 agent provenance 记录信息来源和流转路径，但通常不输出可阻断执行的许可状态。
4. tool authorization 判断工具和参数是否允许，但不判断模型生成该参数时是否实际看到必要上下文。
5. human approval 依赖用户点击，但不能证明 agent 后续工具调用仍保留审批约束。
6. audit trail 事后记录轨迹，难以在许可签发前阻断上下文不足导致的错误执行。

## 五、发明点概述

本发明的核心不是“管理上下文”或“记录 provenance”，而是将高风险工具调用许可绑定到模型决策时的动作相关上下文保留证明。

本发明将智能体高风险工具调用的执行许可建模为如下状态机：

```text
ToolCallCandidate
-> ActionImpactClass
-> RequiredContextObligation
-> PromptAssemblyManifest
-> ContextRetentionEvidence
-> ContextSufficiencyState
-> RegroundingPlan
-> PermitDecision
-> ContextAdequacyEvidence
```

其中：

1. `ToolCallCandidate` 是智能体生成但尚未执行的高风险工具调用候选。
2. `RequiredContextObligation` 是根据工具调用影响类别生成的上下文保留义务，描述本次决策必须看见哪些上下文证据、以何种形式保留、时效要求和缺失处理策略。
3. `PromptAssemblyManifest` 是生成该工具调用候选的模型推理输入装配清单，记录模型实际可见的上下文单元、摘要来源、检索结果、memory 快照和 token 位置等。
4. `ContextRetentionEvidence` 是对每个必需上下文锚点进行匹配后得到的保留证据，包括原文保留、经认证摘要保留、可追溯引用、缺失、过期、冲突或污染等状态。
5. `ContextSufficiencyState` 是许可前状态机输出，决定是否允许签发许可、要求重新 grounding、重新审批、切换执行模式或拒绝执行。
6. `ContextAdequacyEvidence` 是最终审计证据，证明某次高风险工具调用不仅参数合法，而且生成该调用时模型具备必要上下文。

## 六、要解决的技术问题

本发明要解决的技术问题包括：

1. 如何针对不同高风险工具调用自动确定“本次决策必须保留的上下文”。
2. 如何证明模型生成该工具调用时实际看到了这些上下文，而不是仅在历史日志中曾经出现过。
3. 如何区分原文保留、可信摘要、可追溯引用、缺失、过期、冲突和污染上下文。
4. 如何在上下文不足时自动触发重新注入、重新检索、重新审批、降级执行或拒绝许可。
5. 如何生成可审计证据，证明执行前的模型决策上下文是充分的。

## 七、技术方案

### 7.1 接收高风险工具调用候选

系统接收智能体输出的 `ToolCallCandidate`，但不立即执行。工具调用候选至少包括：

- `toolName`
- `toolArguments`
- `agentId`
- `conversationId`
- `inferenceId`
- `requestHash`
- `targetResource`
- `executionMode`

系统根据工具类型、目标资源、动作类型、环境和影响范围确定 `ActionImpactClass`。示例：

- `external_message_send`
- `database_write`
- `production_deploy`
- `payment_execution`
- `account_permission_change`
- `customer_state_mutation`
- `source_code_commit`

### 7.2 生成上下文保留义务

系统根据 `ActionImpactClass`、目标资源和策略规则生成 `RequiredContextObligation`。

示例：

```json
{
  "toolCallDigest": "sha256:...",
  "actionImpactClass": "production_deploy",
  "requiredAnchors": [
    {
      "anchorType": "user_instruction",
      "minimumRetentionMode": "verbatim",
      "freshnessWindowSeconds": 3600
    },
    {
      "anchorType": "approval_note",
      "minimumRetentionMode": "verbatim",
      "freshnessWindowSeconds": 1800
    },
    {
      "anchorType": "system_policy",
      "minimumRetentionMode": "certified_summary",
      "freshnessWindowSeconds": 300
    },
    {
      "anchorType": "tool_result",
      "minimumRetentionMode": "certified_summary",
      "freshnessWindowSeconds": 600
    }
  ],
  "missingAnchorAction": "reground_or_deny"
}
```

该义务不是通用上下文质量指标，而是针对待执行动作生成的许可前置条件。

### 7.3 获取 prompt 装配清单

系统获取生成该 `ToolCallCandidate` 的同一次模型推理对应的 `PromptAssemblyManifest`，该清单至少包括：

- `inferenceId`
- `modelId`
- `promptDigest`
- `contextUnitDigests`
- `contextUnitOrder`
- `tokenPositionRanges`
- `summaryDerivationDigests`
- `retrievalQueryDigest`
- `retrievedDocumentDigests`
- `memorySnapshotDigest`
- `systemPolicyDigest`

关键点是：必须绑定到生成工具调用候选的同一次模型推理，而不是事后任意补齐上下文。

### 7.4 生成上下文保留证据

系统将 `RequiredContextObligation` 与 `PromptAssemblyManifest` 匹配，为每个必需上下文锚点生成 `ContextRetentionEvidence`：

- `verbatim`：必需上下文原文出现在模型输入中。
- `certified_summary`：必需上下文通过可验证摘要出现在模型输入中，摘要可追溯到原文。
- `retrievable_reference`：模型输入中存在可解析引用，并在许可前可检索验证。
- `missing`：必需上下文未出现在模型输入或可验证引用中。
- `stale`：上下文存在但超过时效要求。
- `conflicting`：存在与动作相冲突的上下文但未被纳入决策。
- `tainted`：上下文来自低可信来源或被不可信内容污染。

### 7.5 输出上下文充分性状态

系统根据所有上下文保留证据输出 `ContextSufficiencyState`：

- `Sufficient`
- `SufficientByCertifiedSummary`
- `RegroundRequired`
- `ReapprovalRequired`
- `Stale`
- `Conflicting`
- `Contaminated`
- `Insufficient`

### 7.6 许可状态转移

系统根据 `ContextSufficiencyState` 决定 `PermitDecision`：

1. `Sufficient`：允许签发高风险工具调用许可。
2. `SufficientByCertifiedSummary`：在策略允许摘要保留的情况下签发许可。
3. `RegroundRequired`：重新注入缺失上下文，要求模型基于更新后的上下文重新生成工具调用。
4. `ReapprovalRequired`：审批约束缺失或过期时，要求重新审批。
5. `Stale`：重新检索资源状态或策略状态。
6. `Conflicting`：拒绝许可或要求人工解决冲突。
7. `Contaminated`：拒绝许可、切换 sandbox 或清除污染上下文后重试。
8. `Insufficient`：拒绝签发许可。

### 7.7 生成审计证据

系统生成 `ContextAdequacyEvidence`，至少包括：

- `toolCallDigest`
- `requiredContextObligationDigest`
- `promptAssemblyManifestDigest`
- `contextRetentionEvidenceDigest`
- `contextSufficiencyState`
- `regroundingApplied`
- `permitIssued`
- `permitOutcome`
- `denialReason`

该证据用于证明高风险工具调用在执行前满足决策上下文充分性要求。

## 九、典型实施例

### 9.1 邮件发送场景

用户在长任务中要求：“整理合同，但不要发给外部客户，先给我预览。”后续上下文被压缩，agent 生成 `send_email(to=customer@example.com)`。

系统生成的 `RequiredContextObligation` 要求最新用户指令原文保留。`PromptAssemblyManifest` 中未发现该指令，只有摘要“prepare contract”。系统输出 `ContextSufficiencyState=Insufficient`，拒绝签发邮件发送许可。

技术效果：避免合法邮件工具和合法参数在缺失用户限制的情况下被执行。

### 9.2 CI/CD 部署场景

审批备注为“仅允许 dry-run，不允许 production deploy”。agent 后续上下文中只保留“approved”，生成 production deploy 调用。

系统要求审批备注原文保留。由于 prompt 中未包含“仅允许 dry-run”，输出 `ReapprovalRequired` 或 `Insufficient`，拒绝 production deploy。

技术效果：防止审批约束在 agent 长链路中被压缩为泛化 approve。

### 9.3 数据库写入场景

上游查询工具返回“订单已取消”，但 agent 当前上下文只保留旧摘要“订单待处理”，生成数据库写入。

系统要求关键上游工具结果以可信摘要保留，且摘要必须包含取消状态。摘要验证失败后输出 `RegroundRequired`，重新注入上游工具结果并要求模型重新决策。

技术效果：避免基于过期或失真的工具结果执行写操作。

### 9.4 RAG 反证场景

RAG 检索到政策文档，其中包含“该客户所在地区不得自动续费”的反证信息，但摘要只保留了续费步骤。agent 生成续费 API 调用。

系统将反证文档标记为 `negative_evidence`，要求该锚点必须在 prompt 中原文保留或经认证摘要保留。若未保留，输出 `Conflicting`，拒绝许可。

技术效果：将遗漏反证信息转化为可阻断的许可状态，而非事后审计问题。

## 十、与现有技术的区别

### 10.1 区别于 context engineering

context engineering 关注如何选择、组织、压缩或检索上下文，以提升模型效果。本发明关注的是：在高风险工具调用许可前，证明生成该工具调用的模型输入满足动作相关上下文保留义务。

### 10.2 区别于 dynamic context window management

dynamic context window management 解决 token budget 和对话质量。本发明不只是决定放哪些上下文，而是根据待执行动作生成必需上下文义务，并将该义务的覆盖状态作为 permit 签发条件。

### 10.3 区别于 provenance / audit

provenance 和 audit 记录信息来源和流转。本发明在工具执行前根据 provenance 计算 `ContextSufficiencyState`，并在不足时阻断或重新 grounding。

### 10.4 区别于 tool authorization

tool authorization 判断工具和参数是否允许。本发明判断模型生成该工具调用时是否实际看到足以支持该参数的必要上下文。

### 10.5 区别于 human approval

human approval 记录人是否同意。本发明判断审批约束是否在后续模型决策中被保留；如果审批备注被压缩为泛化 approve，则不允许执行超出备注约束的动作。

## 十一、为什么不是功能堆积

本发明不是“上下文管理 + 审计 + 授权 + 重试”的简单组合。其技术统一点是：

> 以待执行高风险工具调用为触发点，生成动作相关上下文保留义务；以生成该调用的同一次模型推理输入为证明对象；以每个上下文锚点的保留证据为状态转移条件；以工具执行许可作为状态机出口。

如果没有 `RequiredContextObligation`，系统只是普通上下文管理。
如果没有 `PromptAssemblyManifest`，系统无法证明模型当时实际看到什么。
如果没有 `ContextRetentionEvidence`，系统无法判断每个义务是否被覆盖。
如果没有 `ContextSufficiencyState`，系统无法把证据转化为执行控制。
如果没有 `PermitDecision`，系统只是事后审计。

这些组件围绕同一个技术问题形成闭环：如何在执行前证明模型决策上下文充分。

## 十一之一、与 PCAS、CAAM、Agent-C 的重点区别

PCAS、CAAM 和 Agent-C 是本案最需要重点规避的三类近似公开。

### 11.1 与 PCAS 的区别

PCAS 的强点是 dependency graph、tool call、tool result、message provenance 和 reference monitor。它可以表达 agentic system state 中的因果依赖，并基于策略判断是否允许执行。

本案不主张通用因果图策略编译。本案的证明对象是：

> 生成某个高风险工具调用候选的同一次模型推理输入。

本案不是判断“系统历史中是否存在某个审批或工具结果节点”，而是判断：

> 该审批备注、用户限制、上游工具结果或反证信息，是否在生成该 tool call 的 prompt 装配清单中以规定保留模式实际可见。

因此，权利要求应强调 `PromptAssemblyManifest` 与同一次推理绑定，以及 `ContextRetentionEvidence` 按每个 required anchor 生成。

### 11.2 与 CAAM 的区别

CAAM 的强点是 contextual authorization mesh、sidecar tool-call interception、Inference Boundary hash、SCO metadata、contextual risk score 和 JIT scoped token。

本案不主张 mesh、sidecar、SCO、JIT token 或 contextual risk score。本案主张：

> 根据待执行高风险工具调用生成动作相关上下文锚点保留义务，并将该义务与生成该 tool call 的 prompt 装配清单逐项匹配。

`Inference Boundary hash` 可以证明某个推理边界或配置，但不能直接证明“某个动作必要上下文锚点是否在本次模型输入中原文保留、经认证摘要保留、过期、缺失、冲突或污染”。本案的状态机输出来自逐锚点保留证据，而不是总体 contextual risk score。

### 11.3 与 Agent-C 的区别

Agent-C 的强点是 temporal / state-dependent constraints、runtime guarantee、SMT 检查和 constrained generation，用于阻止不合规工具调用。

本案不主张任意时序约束或通用不合规工具调用检测。本案限定在：

> 高风险工具调用所需上下文锚点的保留义务、保留模式、时效、冲突和污染状态。

本案的关键状态转移不是“某个 temporal property 是否满足”，而是：

```text
required anchor missing / stale / conflicting / tainted
-> ContextSufficiencyState changes
-> permit denied / reground / reapproval
```

### 11.4 建议写入权利要求的差异限定

为规避 PCAS、CAAM 和 Agent-C，独立权利要求应尽量写入以下限定：

1. 所述 prompt 装配清单为生成所述高风险工具调用候选的同一次模型推理对应的装配清单。
2. 所述上下文保留义务包括至少一个动作相关上下文锚点及其最低保留模式。
3. 所述上下文保留证据按每个动作相关上下文锚点分别生成。
4. 当任一必需上下文锚点处于缺失、过期、冲突或污染状态时，拒绝签发许可或触发重新 grounding / 重新审批。
5. 所述许可绑定所述上下文保留义务、prompt 装配清单和上下文保留证据的摘要。

## 十二、拟保护的权利要求草案

### 12.1 独立方法权利要求

一种基于上下文保留证明状态机的智能体高风险工具调用许可控制方法，其特征在于，包括：

1. 接收智能体生成的高风险工具调用候选；
2. 根据所述高风险工具调用候选确定动作影响类别；
3. 根据所述动作影响类别生成上下文保留义务，所述上下文保留义务包括至少一个必需上下文锚点、所述必需上下文锚点的保留模式、时效要求和缺失处理策略；
4. 获取生成所述高风险工具调用候选的模型推理对应的 prompt 装配清单；
5. 将所述上下文保留义务与所述 prompt 装配清单进行匹配，生成每个必需上下文锚点的上下文保留证据；
6. 根据所述上下文保留证据生成上下文充分性状态；
7. 当所述上下文充分性状态满足所述动作影响类别对应的许可条件时，签发用于执行所述高风险工具调用候选的许可；
8. 当所述上下文充分性状态不满足所述许可条件时，执行重新注入上下文、重新检索上下文、重新请求审批、切换执行模式或拒绝签发许可中的至少一种；
9. 将所述上下文保留义务、prompt 装配清单、上下文保留证据、上下文充分性状态和许可结果写入审计记录。

### 12.2 独立系统权利要求

一种基于上下文保留证明状态机的智能体高风险工具调用许可控制系统，其特征在于，包括：

1. 工具调用接收模块，用于接收智能体生成的高风险工具调用候选；
2. 动作影响分类模块，用于确定所述高风险工具调用候选的动作影响类别；
3. 上下文义务生成模块，用于根据所述动作影响类别生成上下文保留义务；
4. prompt 装配清单获取模块，用于获取生成所述高风险工具调用候选的模型推理对应的 prompt 装配清单；
5. 上下文保留证据生成模块，用于匹配上下文保留义务和 prompt 装配清单；
6. 上下文充分性状态机模块，用于根据上下文保留证据生成上下文充分性状态；
7. 许可决策模块，用于根据上下文充分性状态签发许可、执行重新 grounding、重新审批、降级执行或拒绝许可；
8. 审计证据模块，用于生成上下文充分性审计证据。

### 12.3 从属权利要求方向

1. 如权利要求一所述的方法，其中所述必需上下文锚点包括用户最新指令、系统策略、审批备注、上游工具结果、资源状态、检索文档、反证信息或任务转交约束中的至少一种。
2. 如权利要求一所述的方法，其中所述保留模式包括原文保留、经认证摘要保留、可检索引用、显式重新确认中的至少一种。
3. 如权利要求一所述的方法，其中所述 prompt 装配清单包括模型推理标识、prompt 摘要、上下文单元摘要、上下文单元顺序、token 位置范围、摘要派生摘要、检索查询摘要或 memory 快照摘要。
4. 如权利要求一所述的方法，其中所述上下文保留证据包括原文保留、经认证摘要保留、可追溯引用、缺失、过期、冲突或污染中的至少一种状态。
5. 如权利要求一所述的方法，其中所述上下文充分性状态包括充分、经认证摘要充分、需要重新 grounding、需要重新审批、过期、冲突、污染或不足。
6. 如权利要求一所述的方法，其中当审批约束缺失或过期时，系统拒绝签发真实执行许可并要求重新审批。
7. 如权利要求一所述的方法，其中当反证上下文未被保留时，系统生成冲突状态并拒绝许可。
8. 如权利要求一所述的方法，其中当必需上下文仅存在未认证摘要时，系统重新注入原始上下文并要求模型重新生成工具调用候选。
9. 如权利要求一所述的方法，其中所述许可绑定所述高风险工具调用候选、上下文保留义务、prompt 装配清单和上下文保留证据的摘要。
10. 如权利要求一所述的方法，其中审计记录包括上下文充分性状态、许可结果和拒绝原因。

## 十三、可验证技术效果

本发明至少具有以下技术效果：

1. 在工具调用执行前发现模型决策时缺失必要上下文的问题。
2. 防止因上下文压缩、驱逐、摘要失真、状态过期或污染导致的错误高风险操作。
3. 将上下文管理从效果优化机制转化为执行许可控制机制。
4. 使企业能够证明某次高风险工具调用在执行前具备充分决策上下文。
5. 在上下文不足时自动触发重新 grounding、重新审批、降级执行或拒绝许可。
